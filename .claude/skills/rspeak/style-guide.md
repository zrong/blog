# 写作风格指南

基于 2007-2026 年博客文章分析提取的风格规则。校对时以此为标准。

这份文档包含两类内容：

1. **具体格式规范**：用于校对时直接检查和修正。
2. **写作风格指导**：用于理解作者稳定的表达方式、结构偏好和判断逻辑。

校对时，两者都要参考。不要只看格式，也不要只模仿语气。目标不是把文章改成统一模板，而是在不损失作者个人表达的前提下，修正常见错误并保持稳定风格。

## 标点符号

- 中文正文使用中文标点（，。！？；：）
- 括号：正文中使用中文括号（），代码/技术标识用英文括号 ()
- 引号：使用直角引号「」代替中文弯引号""，嵌套引号使用『』
- 英文引号仅用于代码相关引用
- 省略号使用 `……`（两个中文省略号字符），不用 `...`
- 破折号使用 `——`（两个中文破折号），不用 `--`
- 破折号常用于引出关键判断或补充说明，例如：「这个问题的本质不是『路径错了』，而是——运行服务的登录身份变了，用户主目录也跟着变了。」
- 删除线可用于自我纠正或幽默，例：`~~很可能~~ 一定`。不频繁，但出现时有明确的「纠正/调皮」意图

## 加粗用法

加粗是核心说理工具，不是格式装饰：

- 加粗内容是**判断、结论、转折**，不是术语或名词
- 例：「**不是全开，而是白名单放行。**」「**完全不够用。**」
- 加粗可放在段首提出观点：「**一个模型打天下，也不是不行。**」
- 加粗可强调警告或限制：「**它只能作为你的私聊对象。**」
- 偶尔用连续加粗构成递进
- 范围声明也可加粗：「**本文的讨论局限于 15 人以内的纯游戏研发团队。**」
- 不加粗术语名、工具名——这些用反引号包裹

## Emoji 使用

- 正文中几乎不使用 emoji，风格克制
- 偶尔在括号内旁白处出现 😄 😝 或颜文字 `╮(╯▽╰)╭`
- 标题和 description 字段中不用 emoji

## 中英文混排

- 中文与英文单词之间**加空格**（如：使用 Python 编写）
- 中文与数字之间**加空格**（如：共 10 篇文章）
- 英文专有名词保持原始大小写（如 JavaScript、HTTP、API、macOS）
- 代码片段用反引号 `` `code` `` 包裹
- 英文标点紧跟英文单词，与后续中文之间加空格
- 数字与中文单位之间加空格（如 `10 篇`）
- 数字与英文单位之间加空格（如 `100 MB`）

## 段落与结构

- 段落控制在 2-5 句话，避免过长
- 技术文章用 `##` 分章节，`###` 分小节
- 标题后不加标点
- `<!--more-->` 放在开头 1-3 段之后，作为摘要分割
- 段落之间用空行分隔，不使用多余空行（连续两个以上空行）
- 开篇不要过度铺垫。通常前两段内就要进入真实场景、核心问题或明确的判断
- 读者应能在较短时间内判断「这篇文章对我有没有用」
- 避免大段文字不分段。如果一个句子超过三行，通常意味着需要拆分
- 避免流水账式记录，不写「我先做了 A，然后做了 B，然后做了 C」式堆叠
- 技术文章常见结构为：
  1. 背景：碰到了什么问题
  2. 最简单的解法是什么
  3. 这个解法有什么代价
  4. 所以我的目标是……
  5. 具体方案（配置 + 代码）
  6. 实现细节（改了哪些文件，为什么这样改）
  7. 验证结果
  8. 真正的总结（这次工作里最值得记录的不是 X，而是 Y）
- 结尾通常不止于「问题解决了」，而是回到更值得记录的判断、经验或原则

## 语气与人称

### 自称规则

- **作者自称统一使用「曾老师」**，校对时若发现自称不一致（如「我」「笔者」等），应统一改为「曾老师」
- 第一人称「我」用于描述亲身经历、感受和操作步骤时仍可保留，但叙述性自称一律用「曾老师」
- 例：「曾老师目前已经有三只龙虾」「曾老师在实际开发的项目中进行了尝试」「曾老师刷数据的时候发现了一个分享次数尖峰」
- 「曾嵘说/曾嵘胡扯」批注系统：读书笔记中用 `> **曾嵘说：**` 或 `> 曾嵘：` 引用块格式，把自己的思考与原书内容在视觉上区分，形成「正文 + 批注」的双层阅读体验

### 对读者的称呼

- 常用「同学」称呼读者，例：「建议买了 Coding Plan 的同学去领一下」「对于懒得折腾的同学」
- 「你/你们」用于直接对话和引导思考
- 「大家」用于泛指行业群体
- 不用「读者」「用户」等疏远的称呼

### 语气基调

- 自然口语化，避免过度正式的书面语
- 技术文章可用「我们」引导操作步骤（有时指团队，有时泛指行业，上下文切换自然）
- 影评/文化类文章允许主观评价
- 语气应理性、克制，但可以有立场，不必假装中性
- 不回避判断，也不把结论强加给读者
- 读者默认是「和我一样动手解决问题的人」，不是完全不懂技术的新手
- 常从真实问题切入，而不是空泛背景介绍
- 可以使用自问自答、反问等方式推进论述，但要节制
- 校对时应优先保留作者的现场感、判断感和问题意识，不要统一改成公文式表达

## 整体风格定位

- **语气**：第一人称，读者视角为「和我一样动手解决问题的人」
- **语种**：纯中文，中英混排仅限于必要的术语、工具名、代码片段
- **基调**：理性、克制、有立场，不回避判断，也不强加结论
- **目标读者画像**：会自己搭服务、有动手能力、不是纯新手但也不需要手把手教的开发者

## 标题风格

- 标题通常是**一句话描述问题或立场**，而不是干巴巴的技术名词堆砌
- 喜欢用「但」字连接前后两个对立面，形成张力
- 例如：「为 nanobot 打开内网能力，但不关闭安全」
- 标题本身带有判断，不是中性描述

规律总结：

- 标题 = 一个有争议的立场，或一个有张力的前提
- 不用 `How to` 式标题
- 不用名词堆砌式标题
- 标题即是观点

## 开篇节奏

- 不废话，直接切入真实场景
- 第一句话通常是「我遇到了一个问题」，而不是「最近我学到了一个很有趣的技术」
- 背景铺垫通常不超过两段，越短越好
- 读者需要能在一分钟内判断「这篇文章对我有没有用」

典型模式：

1. 真实场景（我碰到什么问题）
2. 需求合理性（这个需求本身不奇怪）
3. 但有障碍（默认做不到，或最简单的方案代价太大）
4. 再定位目标（我的目标不是粗暴地绕过去，而是在边界内解决它）

## 段落与句式节奏

### 单句成段

- 极频繁使用单句独占一段来强调关键判断或转折
- 例：「这其实不是什么 bug」「**我的需求也是真的。**」「也不尽然。」「我选 3。」
- 起到阅读节奏中的「呼吸点」和「强调」作用

### 短句偏好

- 大量使用短句，一段通常不超过三句
- 避免冗长的从句嵌套
- 如果一个句子超过三行，通常意味着需要拆分

### 判断句式

- 喜欢用「这件事本身是对的」「这是合理的」这类句式，为背景或需求正名
- 经常用「但我的需求也是真的」这类表达，把讨论从抽象规范拉回真实处境
- 不回避「这么做快不快？快。这么做危险不危险？也危险。」这类直接反问

### 确认与承接

- 「是的」「确实」「的确」用于在陈述令人意外的结论后加强语气
- 例：「是的，留存和用户时长都挺不错的，但就是不赚钱。」
- 「当然」常用于让步或预判反驳，先承认一面再转折
- 例：「当然也可以是休闲游戏」「当然，要求非策划岗位的同学提供数据分析……」

### 直接反驳

- 「拜托」式直接反驳，把读者当对话对象，带不耐烦的坦诚
- 例：「拜托！这游戏可是全中国人都在玩！」「拜托，你几个月做了 200 个小游戏，有啥用呢？」

### 反问与自问自答

- 经常自问自答推进论述
- 反问语气帮助读者建立认同感
- 例如：「这么做快不快？快。这么做危险不危险？也危险。」

### 排比三段式

- 三段平行结构制造节奏感
- 例：「快速上线、快速试错、快速放弃」

### 假设与推演

- 先假设再推演的句式
- 例：「如果把「立项」看做确定「下一代」产品基因的可行性动作，我们就必须想清楚：我们的基因是什么？」

### 破折号使用

- 常用破折号引出关键判断或补充说明
- 例如：「这个问题的本质不是『路径错了』，而是——运行服务的登录身份变了，用户主目录也跟着变了。」

## 技术内容的表达方式

### 定量优先于定性

- 不满足于「改动很小」，而是说「7 个文件，93 行新增，15 行删除」
- 不满足于「验证通过了」，而是说「Jina 返回 451，但回退到 readability 依然拿到正文」
- 数字和具体行为比形容词更有说服力

### 清单式列举

- 用破折号或「例如：」引出技术细节
- 避免大段描述，改用清单让信息密度更高

### 代码片段的处理

- 代码块标注语言：` ```python `
- 行内代码用反引号包裹
- 术语首次出现时可附加简要解释
- 技术缩写保持大写原样（HTTP、API、URL、SDK）
- 命令行工具名保持原样小写（如 `git`、`npm`、`uv`）
- 只展示最必要的片段，不做完整示例堆砌
- 强调代码和配置应尽量可直接复制使用
- JSON 配置展示是常见形式之一，但不是唯一形式
- 每次展示代码，背后都应回答一个问题：这样做的好处是什么

### 技术判断的语气

- 常用「这里有个很重要的点：」用于引出容易被忽略的细节
- 常用「真正重要的不是……而是……」用于把讨论从表象拉回本质
- 不轻易说「最佳实践」，更常用「更稳的办法」「更可控的方案」

## 说理逻辑结构

### 典型论证模式

1. 背景：碰到了什么问题
2. 最简单的解法是什么
3. 这个解法有什么代价
4. 所以我的目标是……
5. 具体方案（配置 + 代码）
6. 实现细节（改了哪些文件，为什么这样改）
7. 验证结果
8. 真正的总结（这次工作里最值得记录的不是 X，而是 Y）

### 核心判断句

- 「很多时候，技术实现不是最难的。如何以最小的改动，把正确的事情做进去，才是难点。」
- 「技术方案真正成熟的标志，从来都不是它『终于能用了』，而是它在能用之外，还尽量保持了边界、克制和可维护性。」
- 「对于一个本地自用的 agent 来说，访问局域网资源是很自然的诉求。但『自然的诉求』，并不意味着可以『随便地实现』。」

### 收敛式结尾

- 结尾通常会拉回一个更大的视角
- 不止步于「问题解决了」，而是「解决过程中这几个判断是最值得记录的」
- 结尾最后一句通常是一个价值判断，而不是技术总结
- 可用「全文完」简洁收尾，不用「感谢阅读」
- 可用「P.S.」添加与正文不完全平行但相关的补充信息，类似脚注
- 系列文章末尾附系列链接列表，构建网状知识体系

### 从失败讲起

- 坦诚承认失败作为论证的一部分，不美化
- 先证伪，再证实：先分析失败，最后才给出方法论
- 例：「就从失败讲起吧」

### 先给结论，再给推导

- 很少按时间顺序叙述，而是按「结论优先」的顺序
- 例：「先说结论：nanobot 不能访问局域网，并不是某一个工具单独做了限制」

### 表格作为判断框架

- 表格用于呈现二分法的判断框架，而非单纯罗列数据
- 例：换核 vs 换皮对比、超休闲 vs 中度休闲对比

### 范围限定式开篇

- 开篇直接划定讨论边界
- 例：「**本文的讨论局限于……**」

## 代码与术语

- 代码块标注语言：` ```python `
- 行内代码用反引号包裹
- 术语首次出现时可附加简要解释
- 技术缩写保持大写原样（HTTP、API、URL、SDK）
- 命令行工具名保持原样小写（如 `git`、`npm`、`uv`）
- 代码片段不必追求完整示例，优先保留最必要、可直接复制的部分
- 不为展示而展示代码；每段代码都应服务于当前判断或解决方案

## 列表

- 列表项若为完整句子，末尾加句号。
- 列表项若为短语片段，末尾不加标点
- 列表项之间不加空行
- 技术细节、验证结果、注意事项优先用列表表达，避免大段信息堆叠

## 用词偏好

### 高频口语化用词

以下用词在文章中反复出现，属于作者稳定的表达习惯，校对时应保留：

- 「顺手」「坑」「抓狂」「简单粗暴」「薅羊毛」「白嫖」「标题党」「卡壳」
- 「拉满」（例：细节拉满、张力拉满）、「量大管饱」「满天飞」
- 「不科学」（表达困惑时，例：「百思不得其解，这不科学啊……」）
- 「DUANG 的一下」（形容快速完成）
- 「压榨」（例：进一步压榨 AI 牛马的能量）
- 经典转折词：「然而」（最高频）、「毕竟」

### 括号内的幽默与话里有话

括号常用于三种幽默补充：
- **吐槽**：（锯腿那个不算哈）（这不门外汉么）（注意：运气也是实力的一部分）
- **拼音暗示**：获取更大成（li）就（yi）——用拼音标注「利益」，制造「话里有话」效果
- **免责声明**：注意：上述引言并未经过验证。仅作为情感支持，不作为论据支撑

### 古文与名言引用

- 偶尔引用古文/名言佐证现代论点，如「君子不器」「善假于物也」「君子和而不同」
- 不频繁，但出现时是刻意的价值锚定

## 不喜欢的东西（写作雷区）

1. **过度注释**：不在代码里写「这是一个函数，用于实现某功能」这种废话
2. **过度抽象**：不为了「优雅」把简单配置搞得像框架设计
3. **过度铺垫**：不开头写三段背景才进入正题
4. **名词堆砌标题**：不用 `How to XXX`、`XXX 入门指南` 类标题
5. **流水账式记录**：不写「我先做了 A，然后做了 B，然后做了 C」
6. **机械短语模仿**：不直接复制别人的句式，而是学习背后的逻辑结构

## 风格模仿原则

- 借用结构与语气，而非机械复制短语
- 模仿判断方式，而非模仿措辞
- 接受直接起草，不需要先问「你觉得这样写行不行」
- 校对时优先保留作者的立场、节奏和克制感
- 不为了「更像某种写作模板」而抹平作者个性

## 参考句式清单

以下句式可作为风格参考，但不应机械套用：

- 「这件事说起来不复杂，真做起来，坑还不少。」
- 「如果以为……那就太乐观了。」
- 「这个坑很典型。」
- 「最后排查下来，原因不是……而是……」
- 「解决办法并不复杂：」
- 「这里最容易被忽略的一点是：」
- 「这一步很关键。」
- 「这些验证虽然不花哨，但很必要。」
- 「很多时候，技术实现不是最难的。」
- 「真正重要的不是……而是……」
- 「全文完」
- 「是的，……，但……」
- 「拜托！……」
- 「当然，……」
- 「先说结论：……」
- 「就从失败讲起吧」
- 「经验不一定正确，**但保真，保熟。**」
- 「被你知道了，你也干不了的事，才是核心竞争力。」

## 按文体校对的侧重点

- 技术文章：优先保证结构清晰、步骤完整、术语准确、代码可复制
- 工具/配置类文章：优先保证真实场景、方案边界、验证结果都说清楚
- 经验记录/随笔：允许更强的个人叙述感，但仍应避免空泛抒情
- 影评/剧评/文化类文章：允许主观判断与评价，不必强行改成技术说明文口吻
- 不同文体可以有不同表达密度，但都应避免过度铺垫、过度抽象和机械模仿

## 常见错误模式（重点校对）

- **「的/地/得」混用**：形容词+的+名词，副词+地+动词，动词/形容词+得+补语
- **中文标点与英文标点混用**：句末用 `.` 而非 `。`，逗号用 `,` 而非 `，`
- **中英文之间缺少空格**：如「使用Python」应为「使用 Python」
- **多余空行或缺少分段**：连续超过一个空行，或大段文字未分段
- **引号不规范**：使用 "" 而非「」
- **数字与单位之间缺少空格**：如 `10篇`、`100MB`
- **过度书面语**：把原本自然、直接的表达改得过分正式
- **过度铺垫**：开头写了很多背景，迟迟不进入问题
- **名词堆砌标题**：只有术语，没有判断或张力
- **流水账式叙述**：只有步骤记录，没有问题意识、判断和结论
- **机械短语模仿**：只复制表面句式，没有保留原文逻辑和语气
- **自称不一致**：未统一使用「曾老师」自称，混用「我」「笔者」等
- **加粗误用**：加粗术语或工具名（应用反引号），而非加粗判断和结论
- **Emoji 泛滥**：在正文核心论述中使用 emoji

## 后续写作辅助

如需按此风格继续写作，最好明确以下信息：

1. **需求背景**：在做什么事、碰到了什么问题
2. **技术判断**：最在意的原则（如「不改大重构」「改动尽量小」）
3. **需要包含的内容**：配置示例、代码片段、流程图（Mermaid）、截图
4. **不需要的内容**：版本号展示、过度铺垫、与主题无关的背景

按这个原则，直接输出完整初稿即可，不需要先问「你觉得这样写行不行」。
