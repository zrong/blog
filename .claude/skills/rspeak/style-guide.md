# 写作风格指南

基于 2007-2026 年博客文章分析提取的风格规则。校对时以此为标准。

这份文档包含两类内容：

1. **具体格式规范**：用于校对时直接检查和修正。
2. **写作风格指导**：用于理解作者稳定的表达方式、结构偏好和判断逻辑。

校对时，两者都要参考。不要只看格式，也不要只模仿语气。目标不是把文章改成统一模板，而是在不损失作者个人表达的前提下，修正常见错误并保持稳定风格。

## 标点符号

- 中文正文使用中文标点（，。！？；：）
- 括号：正文中使用中文括号（），代码/技术标识用英文括号 ()
- 引号：使用直角引号「」代替中文弯引号""，嵌套引号使用『』
- 英文引号仅用于代码相关引用
- 省略号使用 `……`（两个中文省略号字符），不用 `...`
- 破折号使用 `——`（两个中文破折号），不用 `--`
- 破折号常用于引出关键判断或补充说明，例如：「这个问题的本质不是『路径错了』，而是——运行服务的登录身份变了，用户主目录也跟着变了。」

## 中英文混排

- 中文与英文单词之间**加空格**（如：使用 Python 编写）
- 中文与数字之间**加空格**（如：共 10 篇文章）
- 英文专有名词保持原始大小写（如 JavaScript、HTTP、API、macOS）
- 代码片段用反引号 `` `code` `` 包裹
- 英文标点紧跟英文单词，与后续中文之间加空格
- 数字与中文单位之间加空格（如 `10 篇`）
- 数字与英文单位之间加空格（如 `100 MB`）

## 段落与结构

- 段落控制在 2-5 句话，避免过长
- 技术文章用 `##` 分章节，`###` 分小节
- 标题后不加标点
- `<!--more-->` 放在开头 1-3 段之后，作为摘要分割
- 段落之间用空行分隔，不使用多余空行（连续两个以上空行）
- 开篇不要过度铺垫。通常前两段内就要进入真实场景、核心问题或明确的判断
- 读者应能在较短时间内判断「这篇文章对我有没有用」
- 避免大段文字不分段。如果一个句子超过三行，通常意味着需要拆分
- 避免流水账式记录，不写「我先做了 A，然后做了 B，然后做了 C」式堆叠
- 技术文章常见结构为：
  1. 背景：碰到了什么问题
  2. 最简单的解法是什么
  3. 这个解法有什么代价
  4. 所以我的目标是……
  5. 具体方案（配置 + 代码）
  6. 实现细节（改了哪些文件，为什么这样改）
  7. 验证结果
  8. 真正的总结（这次工作里最值得记录的不是 X，而是 Y）
- 结尾通常不止于「问题解决了」，而是回到更值得记录的判断、经验或原则

## 语气与人称

- 第一人称为主，自然口语化
- 技术文章可用「我们」引导操作步骤
- 影评/文化类文章允许主观评价
- 避免过度正式的书面语
- 语气应理性、克制，但可以有立场，不必假装中性
- 不回避判断，也不把结论强加给读者
- 读者默认是「和我一样动手解决问题的人」，不是完全不懂技术的新手
- 常从真实问题切入，而不是空泛背景介绍
- 可以使用自问自答、反问等方式推进论述，但要节制
- 校对时应优先保留作者的现场感、判断感和问题意识，不要统一改成公文式表达

## 整体风格定位

- **语气**：第一人称，读者视角为「和我一样动手解决问题的人」
- **语种**：纯中文，中英混排仅限于必要的术语、工具名、代码片段
- **基调**：理性、克制、有立场，不回避判断，也不强加结论
- **目标读者画像**：会自己搭服务、有动手能力、不是纯新手但也不需要手把手教的开发者

## 标题风格

- 标题通常是**一句话描述问题或立场**，而不是干巴巴的技术名词堆砌
- 喜欢用「但」字连接前后两个对立面，形成张力
- 例如：「为 nanobot 打开内网能力，但不关闭安全」
- 标题本身带有判断，不是中性描述

规律总结：

- 标题 = 一个有争议的立场，或一个有张力的前提
- 不用 `How to` 式标题
- 不用名词堆砌式标题
- 标题即是观点

## 开篇节奏

- 不废话，直接切入真实场景
- 第一句话通常是「我遇到了一个问题」，而不是「最近我学到了一个很有趣的技术」
- 背景铺垫通常不超过两段，越短越好
- 读者需要能在一分钟内判断「这篇文章对我有没有用」

典型模式：

1. 真实场景（我碰到什么问题）
2. 需求合理性（这个需求本身不奇怪）
3. 但有障碍（默认做不到，或最简单的方案代价太大）
4. 再定位目标（我的目标不是粗暴地绕过去，而是在边界内解决它）

## 段落与句式节奏

### 短句偏好

- 大量使用短句，一段通常不超过三句
- 避免冗长的从句嵌套
- 如果一个句子超过三行，通常意味着需要拆分

### 判断句式

- 喜欢用「这件事本身是对的」「这是合理的」这类句式，为背景或需求正名
- 经常用「但我的需求也是真的」这类表达，把讨论从抽象规范拉回真实处境
- 不回避「这么做快不快？快。这么做危险不危险？也危险。」这类直接反问

### 反问与自问自答

- 经常自问自答推进论述
- 反问语气帮助读者建立认同感
- 例如：「这么做快不快？快。这么做危险不危险？也危险。」

### 破折号使用

- 常用破折号引出关键判断或补充说明
- 例如：「这个问题的本质不是『路径错了』，而是——运行服务的登录身份变了，用户主目录也跟着变了。」

## 技术内容的表达方式

### 定量优先于定性

- 不满足于「改动很小」，而是说「7 个文件，93 行新增，15 行删除」
- 不满足于「验证通过了」，而是说「Jina 返回 451，但回退到 readability 依然拿到正文」
- 数字和具体行为比形容词更有说服力

### 清单式列举

- 用破折号或「例如：」引出技术细节
- 避免大段描述，改用清单让信息密度更高

### 代码片段的处理

- 代码块标注语言：` ```python `
- 行内代码用反引号包裹
- 术语首次出现时可附加简要解释
- 技术缩写保持大写原样（HTTP、API、URL、SDK）
- 命令行工具名保持原样小写（如 `git`、`npm`、`uv`）
- 只展示最必要的片段，不做完整示例堆砌
- 强调代码和配置应尽量可直接复制使用
- JSON 配置展示是常见形式之一，但不是唯一形式
- 每次展示代码，背后都应回答一个问题：这样做的好处是什么

### 技术判断的语气

- 常用「这里有个很重要的点：」用于引出容易被忽略的细节
- 常用「真正重要的不是……而是……」用于把讨论从表象拉回本质
- 不轻易说「最佳实践」，更常用「更稳的办法」「更可控的方案」

## 说理逻辑结构

### 典型论证模式

1. 背景：碰到了什么问题
2. 最简单的解法是什么
3. 这个解法有什么代价
4. 所以我的目标是……
5. 具体方案（配置 + 代码）
6. 实现细节（改了哪些文件，为什么这样改）
7. 验证结果
8. 真正的总结（这次工作里最值得记录的不是 X，而是 Y）

### 核心判断句

- 「很多时候，技术实现不是最难的。如何以最小的改动，把正确的事情做进去，才是难点。」
- 「技术方案真正成熟的标志，从来都不是它『终于能用了』，而是它在能用之外，还尽量保持了边界、克制和可维护性。」
- 「对于一个本地自用的 agent 来说，访问局域网资源是很自然的诉求。但『自然的诉求』，并不意味着可以『随便地实现』。」

### 收敛式结尾

- 结尾通常会拉回一个更大的视角
- 不止步于「问题解决了」，而是「解决过程中这几个判断是最值得记录的」
- 结尾最后一句通常是一个价值判断，而不是技术总结
- 可用「全文完」简洁收尾，不用「感谢阅读」

## 代码与术语

- 代码块标注语言：` ```python `
- 行内代码用反引号包裹
- 术语首次出现时可附加简要解释
- 技术缩写保持大写原样（HTTP、API、URL、SDK）
- 命令行工具名保持原样小写（如 `git`、`npm`、`uv`）
- 代码片段不必追求完整示例，优先保留最必要、可直接复制的部分
- 不为展示而展示代码；每段代码都应服务于当前判断或解决方案

## 列表

- 列表项若为完整句子，末尾加句号。
- 列表项若为短语片段，末尾不加标点
- 列表项之间不加空行
- 技术细节、验证结果、注意事项优先用列表表达，避免大段信息堆叠

## 不喜欢的东西（写作雷区）

1. **过度注释**：不在代码里写「这是一个函数，用于实现某功能」这种废话
2. **过度抽象**：不为了「优雅」把简单配置搞得像框架设计
3. **过度铺垫**：不开头写三段背景才进入正题
4. **名词堆砌标题**：不用 `How to XXX`、`XXX 入门指南` 类标题
5. **流水账式记录**：不写「我先做了 A，然后做了 B，然后做了 C」
6. **机械短语模仿**：不直接复制别人的句式，而是学习背后的逻辑结构

## 风格模仿原则

- 借用结构与语气，而非机械复制短语
- 模仿判断方式，而非模仿措辞
- 接受直接起草，不需要先问「你觉得这样写行不行」
- 校对时优先保留作者的立场、节奏和克制感
- 不为了「更像某种写作模板」而抹平作者个性

## 参考句式清单

以下句式可作为风格参考，但不应机械套用：

- 「这件事说起来不复杂，真做起来，坑还不少。」
- 「如果以为……那就太乐观了。」
- 「这个坑很典型。」
- 「最后排查下来，原因不是……而是……」
- 「解决办法并不复杂：」
- 「这里最容易被忽略的一点是：」
- 「这一步很关键。」
- 「这些验证虽然不花哨，但很必要。」
- 「很多时候，技术实现不是最难的。」
- 「真正重要的不是……而是……」
- 「全文完」

## 按文体校对的侧重点

- 技术文章：优先保证结构清晰、步骤完整、术语准确、代码可复制
- 工具/配置类文章：优先保证真实场景、方案边界、验证结果都说清楚
- 经验记录/随笔：允许更强的个人叙述感，但仍应避免空泛抒情
- 影评/剧评/文化类文章：允许主观判断与评价，不必强行改成技术说明文口吻
- 不同文体可以有不同表达密度，但都应避免过度铺垫、过度抽象和机械模仿

## 常见错误模式（重点校对）

- **「的/地/得」混用**：形容词+的+名词，副词+地+动词，动词/形容词+得+补语
- **中文标点与英文标点混用**：句末用 `.` 而非 `。`，逗号用 `,` 而非 `，`
- **中英文之间缺少空格**：如「使用Python」应为「使用 Python」
- **多余空行或缺少分段**：连续超过一个空行，或大段文字未分段
- **引号不规范**：使用 "" 而非「」
- **数字与单位之间缺少空格**：如 `10篇`、`100MB`
- **过度书面语**：把原本自然、直接的表达改得过分正式
- **过度铺垫**：开头写了很多背景，迟迟不进入问题
- **名词堆砌标题**：只有术语，没有判断或张力
- **流水账式叙述**：只有步骤记录，没有问题意识、判断和结论
- **机械短语模仿**：只复制表面句式，没有保留原文逻辑和语气

## 后续写作辅助

如需按此风格继续写作，最好明确以下信息：

1. **需求背景**：在做什么事、碰到了什么问题
2. **技术判断**：最在意的原则（如「不改大重构」「改动尽量小」）
3. **需要包含的内容**：配置示例、代码片段、流程图（Mermaid）、截图
4. **不需要的内容**：版本号展示、过度铺垫、与主题无关的背景

按这个原则，直接输出完整初稿即可，不需要先问「你觉得这样写行不行」。
